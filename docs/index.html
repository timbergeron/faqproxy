Quick start

From source to server.

Build locally, start the relay, then use the familiar Quake console. Replace the example hostname with your actual NetQuake server.

The entire path

  1. Build and run the automated protocol suite.
  2. Start FAQProxy with one fixed upstream server.
  3. Connect your client to the proxy's address.
Build 
git clone https://github.com/timbergeron/faqproxy.git
cd faqproxy
make test
Run the proxy 
./build/faqproxy \
  --listen 0.0.0.0:26000 \
  quake.example.net:26000
Quake console 
connect your.vps.address:26000

Architecture

A relay, not a translator.

The connection handshake is redirected to FAQProxy's public UDP port. Once connected, the native game protocol travels unchanged in both directions.

01 · Client
Quake engine JoeQuake, QS, QSS-M, or another compatible NetQuake client
→
02 · VPS
FAQProxy Handshake routing, packet relay, inspection, and optional demo recording
→
03 · Upstream
NetQuake server One configured IPv4 server and port per FAQProxy process
Important: FAQProxy does not make a QuakeWorld server speak NetQuake, and it does not convert protocol 15 clients into protocol 666 or 999 clients. The client and server must already share a native protocol.

Compatibility

Three protocols. Tested end to end.

The inspector understands each protocol's angle and extension framing while the relay preserves the original payload.

Protocol Family Angle handling Status
15 NetQuake Native 8-bit, ProQuake 16-bit, and FTE2 prediction framing Supported
666 FitzQuake 16-bit client view angles Supported
999 RMQ Protocol-flag-selected angle representation, including float angles Supported

VPS deployment

Small footprint. Clear boundaries.

Use a dedicated user, expose only the chosen UDP port, and let the provided service unit contain the process.

01 / INSTALL

Put it in place

Run sudo make install to place the Unix binary at /usr/local/bin/faqproxy.

02 / FIREWALL

Open one UDP port

Allow inbound UDP 26000 in the provider and host firewalls. Restrict source networks for private use.

03 / SERVICE

Run it contained

Adapt the hardened systemd unit, validate it, then enable it.

Command reference

Only the controls you need.

The final positional argument is always the fixed upstream server. Ports default to the standard NetQuake port, 26000.

-l, --listen
Local IPv4 address and UDP port. Default: 0.0.0.0:26000.
-r, --record-dir
Create one first-person NetQuake .dem recording per accepted connection.
-m, --max-clients
Concurrent session limit from 1 to 64. Default: 32.
-t, --timeout
Established-session idle timeout from 0 to 86,400 seconds. Default: 120.
-v, -vv
Show additional diagnostics, or one line for every forwarded datagram.
--version, --help
Print the installed version or the complete command-line usage.

Demo recording

Native playback, preserved.

Recordings retain the server's original 15, 666, or 999 messages and follow the connected player's view.

  • Existing paths are never overwritten.
  • Unix files use mode 0640.
  • Recording failure never stops packet forwarding.
  • Play back in an engine that supports the recorded protocol.

Security model

Know what the protocol cannot promise.

NetQuake predates modern authenticated challenge handshakes. FAQProxy is intentionally transparent about that boundary.

  • There is no authentication, encryption, or cryptographic source validation.
  • A reachable listener can be used to attempt slot exhaustion or UDP reflection.
  • RCON requests can reach the configured upstream server; use a strong password.
  • Use host and provider firewalls when the proxy is not intended to be public.
  • Keep --max-clients bounded and monitor service logs.
Built in recognition of the tool that showed a proxy could become part of the game.

The original FAQProxy was created in 1997 by Juha “Perkele” Kujala and Ilkka “Zibbo” Rajala of the Finnish Allied Quakers clan. It pioneered external demo recording, spectator and chase-camera experiments, teamplay tools, and programmable routing. That work later evolved into Qizmo.

This repository is a new, independent implementation. All credit for the original FAQProxy concept and historical implementation belongs to Perkele, Zibbo, and its original contributors.
